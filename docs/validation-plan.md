## 1. 验证目标

在真实 Windows 托盘上比较独立工具和 Windhawk 两条路线。用户已接受专用入口和原生入口两种形态，因此优先判断图标行为、恢复能力和维护成本。

## 2. 独立工具探测

先做只读探测，记录当前系统托盘 UIA 树、可见/隐藏元素、可访问名称、支持的操作模式及变化事件。输出“能做 / 不能做 / 不确定”清单，不先隐藏任何图标。

随后在可控样本上验证：

1. 一个测试进程创建两个图标，其中一个动态改变图标和提示文字。
2. 从自有面板操作真实图标，比较单击、双击、右键菜单与原位置的行为。
3. 验证菜单定位、前台窗口、关闭时机及权限边界。
4. 在用户选定的真实应用上复核。PadMouse 可作候选，实际清单待选。
5. 只有原行为可靠后，才验证原图标的隐藏/常驻策略及恢复；变更前记录原状态。

仅能列出名称、启动程序或显示截图，不算通过。UIA 不支持所需行为时，明确报告缺口，再比较辅助组件的成本；不默默将无注入路线改成注入实现。

## 3. Windhawk 基线验证

在虚拟机或适合实验的环境先验证 System Tray Folders，记录其版本、源码提交、Windows build 及其他已启用插件。

核对原生面板中的分组、点击、右键菜单、提示及动态状态；测试停用模块、应用重启、Explorer 重启与异常恢复。当前主机 build `26300.9711` 作为后续目标之一，未实测前不标支持。

同时记录现成模块与本需求的差距：可视化分组管理、常用图标排除、顺序持久化和恢复入口。现成模块可分组，不等于所有建议首版需求都已满足。

| 项目 | 样本 | 记录内容 |

## 5. 路线决策

- 独立路线真实图标操作、状态同步、原位置策略和恢复全部达标，且总代价合理：可优先独立工具。
- 独立路线需大量内部接口或动作不可靠，而 Windhawk 在目标系统稳定：倾向原生插件路线。
- 两者均有关键失败：先收缩兼容范围或记录阻塞项，不把应用快捷方式面板当作完整实现交付。
